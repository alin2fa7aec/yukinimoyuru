# CLAUDE.md

NixOS and home-manager configuration for the desktop `yukiwari`. See `README.md` for the overview and layout.

## Editing

- This repository defines the machine: what is installed and where config files go. The config files themselves, Claude Code's included, live in the separate `dotfiles` repository (checked out at `~/!metier/dotfiles`), which `flake.nix` reads as the non-flake input `inputs.dotfiles`. Edit them there, not here.
- Files that the modules in `home/` place as they are (niri, waybar, wezterm, the global `CLAUDE.md` and so on) are linked straight to the dotfiles checkout with `liveDot`, so edits to them take effect without a rebuild. Files nix reads or transforms (`readFile`, the generated fcitx5 and Qt colors, the nushell config, service arguments, `managed-settings.json`, the kanata config) come from the copy pinned by `flake.lock`. Refer to them with `dotFile "path"` (defined in `flake.nix`), never by joining strings onto `inputs.dotfiles`, so a missing file fails evaluation. After changing those files in dotfiles, run `nix flake update dotfiles` here and apply. To try uncommitted changes to them, pass `--override-input dotfiles path:/home/alin/!metier/dotfiles`.
- `writing-lint.nu` is pinned on purpose, because the PostToolUse hook runs it.
- The `writing-style` skill is not placed from here: its source is in dotfiles, and Claude Code gets it from claude.ai, synced to `~/.claude/skills/synced/`.
- Do not edit `hosts/desktop/hardware-configuration.nix`. It is generated by `nixos-generate-config`.
- The flake only sees files tracked by Git. jj tracks new files on its next snapshot, so run `jj st` before building after adding a file.

## Verifying

The Nix daemon is not reachable from Claude's sandbox, so builds cannot run there. Ask the user to run the lightest command that applies the change. All of them work from Claude Code's `!`:

- Changes to `liveDot` files: nothing to run. niri reloads its config by itself; waybar needs `pkill -SIGUSR2 waybar`
- Changes under `home/` other than `home.packages`, or adding or removing a `liveDot` link: `nu scripts/home-switch.nu` (no sudo)
- Changes to `hosts/`, `home.packages` or `flake.lock`: `sudo -A nixos-rebuild switch --flake .#yukiwari` (asks for the password in fuzzel)
- To only check that the system builds: `nixos-rebuild build --flake .#yukiwari`

The `check` workflow in GitHub Actions evaluates the system and checks the formatting on every push. It does not build, so it does not replace the commands above.

What the sandbox allows:

- Readable: `journalctl` (system and `--user`), unit files under `~/.config/systemd/user` and `result/etc/systemd/system`, and everything in `/nix/store`.
- Programs already built in `/nix/store` can run, which is enough to check some changes after the user builds: `kanata --check --cfg <file>` for the kanata config, `clock-ring --preview out.png --theme ... --wires ...` to see the clock drawn to a PNG.
- Not available: `systemctl` (the user bus included), `sudo` and `gh`. Ask the user.
- The dotfiles checkout can be edited only with the Edit tool. Bash sees it read-only, so ask the user to run jj there.
- Commands for the user's `!` prompt must fit on one line. For a multi-line commit message, use `$'subject\n\nbody'`.

## Commits

Use Conventional Commits with a scope: `feat(desktop): ...`, `fix(kanata): ...`. Scopes in use: `desktop` (niri, waybar and other GUI pieces: `home/desktop.nix`, `home/theme.nix`), `home` (`home/alin.nix`, `home/shell.nix`, `home/tools.nix`), `kanata`, `claude` (`home/claude.nix` and the Claude Code settings), `flake`. Each module in `home/` maps to one scope, so a change that touches one module usually takes that module's scope. Omit the scope for repository-wide changes such as `docs`.
